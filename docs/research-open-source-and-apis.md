# Pair Azure phonemes with homegrown intonation scoring

**No commercial API and no open-source project scores the textbook patterns this app teaches (falling 2-3-1, non-final 2-3-2, rising 2-3, sure-vs-unsure tag questions), so the planned in-house rule engine is the core of the product and the research confirms it.** Every item in the current plan holds up, with fixes to how each one is used. AudioWorklet capture is right, but capture at the device's native rate (Firefox breaks with a 16 kHz AudioContext) and resample yourself. pitchy (0BSD/MIT, 2.8 KB) is right for the live line, but it needs octave-jump repair and is worth testing against SwiftF0 (MIT, top of a 2025 noisy-speech benchmark, runs in the browser). Azure Pronunciation Assessment is still the best-value API: it returns IPA phonemes and syllables with timestamps, plus a Monotone flag. It returns no rise/fall direction, and its prosody scoring is en-US only. CMUdict→IPA works, but you have to write the syllabifier yourself, and any espeak-ng fallback should stay in a build script because espeak-ng is GPL. Azure Neural TTS is the only cloud TTS with a documented pitch-contour control, but only on non-HD voices, and contours are unreliable on short phrases such as tag questions, so keep a Praat-based pitch-editing fallback. Supabase and Claude are confirmed. No gamification library is worth adopting, and audio-LLM judges are too unreliable to grade intonation, so give Claude numbers rather than audio. At ~50 users (roughly 3,000 five-second attempts a month), Azure scoring likely fits inside its 5-hour free tier, and pre-generated TTS reference audio fits inside the 0.5M-character free tier. The real risks are licenses and stale code: essentia.js (AGPL), pitchfinder and espeak-ng WASM (GPL), tldraw (license key), MMS aligners and F5-TTS (non-commercial), and an unlicensed Duolingo-clone tutorial repo.

## No API grades 2-3-1 patterns, so the rule engine stays central

The commercial market splits in two. Some vendors return phoneme timing and a coarse prosody score; very few return any notion of pitch direction, and none returns an F0 contour or pitch levels 1–4. **Azure** gives an utterance-level `ProsodyScore` covering "stress, intonation, speaking speed, and rhythm". Its only word-level intonation error type is `Monotone`, which is detected on the whole utterance and then copied onto every word. It does expose a `SyllablePitchDeltaConfidence` that you can threshold yourself. It also returns **IPA phonemes and syllable groups with Offset/Duration timestamps**, but prosody, IPA and syllables are **en-US only**, and there is no per-syllable stress label ([MS Learn](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-pronunciation-assessment)). **Speechace** is the only vendor verified to return a direction: per-syllable RISE/FALL/FLAT plus a pitch range in Hz, with `include_intonation=1` on the Pro plan, for en-US and en-GB ([Speechace docs](https://api-docs.speechace.com/api-reference/score-text-stress-and-intonation.md)). Its phones are ARPAbet with no IPA option ([Speechace llms-full](https://api-docs.speechace.com/llms-full.txt)). **Alibaba Cloud** scores only whether a sentence that needs a final rise actually rises ([Alibaba help](https://help.aliyun.com/en/document_detail/2996314.html)). **SpeechSuper** advertises "rising/falling tone analysis for sentence endings", but its docs site could not be read, so the response fields are unverified ([SpeechSuper samples](https://github.com/speechsuper/SpeechSuper-API-Samples)).

Audio LLMs do not close the gap. When Gemini-2.5-Pro judged TTS output, it found rising and falling contours "in most cases" but sometimes labelled flat speech as rising or falling, and its agreement with humans was only α≈0.51 ([EmergentTTS-Eval](https://arxiv.org/pdf/2505.23009)). Pronunciation-assessment studies of GPT-4o and Gemini did not score intonation at all ([arXiv 2503.11229](https://arxiv.org/abs/2503.11229v1), [arXiv 2509.14187](https://arxiv.org/pdf/2509.14187)). The practical conclusion is that **2-3-2 detection, level 1–4 quantisation and the check that the pitch peak falls on the nucleus must come from your own F0 analysis**. Azure syllable timestamps tell the rule engine *where* the nucleus is.

## Capture at native rate, track with pitchy, verify against SwiftF0

**Recording (need 1).** The plan's AudioWorklet choice is confirmed, with one design change. Firefox throws NotSupportedError when a microphone stream is connected to an `AudioContext` created with a non-default sample rate, and the bug is still open ([Mozilla 1674892](https://bugzilla.mozilla.org/show_bug.cgi?id=1674892)). So **create a default-rate context, capture Float32 at 48 kHz, feed the pitch tracker from that, and downsample to 16 kHz only for the Azure upload**. A 48→16 kHz FIR decimator is a few dozen lines. The alternative, libsamplerate-js, weighs **1.46 MB gzipped** ([bundlephobia](https://bundlephobia.com/package/@alexanderolsen/libsamplerate-js)). On Safari, `echoCancellation:false` works and also disables AGC ([WebKit 179411](https://bugs.webkit.org/show_bug.cgi?id=179411)). A separate `autoGainControl` constraint is still unimplemented ([WebKit 204444](https://bugs.webkit.org/show_bug.cgi?id=204444)). iOS 26 also has a failure mode where getUserMedia permanently returns NotAllowedError after a media-services reset, so plan a "reload to fix your microphone" screen ([WebKit 319706](https://bugs.webkit.org/show_bug.cgi?id=319706)).

**Pitch tracking (need 2).** pitchy is confirmed. Its GitHub license is now 0BSD and the npm metadata says MIT. It is **2.8 KB gzipped**, but its last release was v4.1.0 in January 2024 and it has no voicing model or octave correction ([GitHub](https://github.com/ianprime0509/pitchy), [npm](https://www.npmjs.com/package/pitchy)). The newer strong option is **SwiftF0**: MIT, 14,386 parameters, ONNX, with a fully client-side demo on onnxruntime-web and per-frame confidence. It ranked **first of 18 trackers (F1@50c 0.781) in the lars76 noisy/reverberant benchmark**, ahead of Praat (0.651) and pYIN (0.506) ([SwiftF0](https://github.com/lars76/swift-f0), [pitch-benchmark](https://github.com/lars76/pitch-benchmark)). No JavaScript tracker, pitchy included, appears in any benchmark. Phrase-final creak and octave errors are exactly what flip a "falling" judgement, so **run pitchy for the live line and evaluate it against SwiftF0 or Parselmouth on 20–50 Thai learner recordings before trusting it for scoring**. Add a clarity gate, a 3–5-frame median filter, octave-jump folding and semitone conversion relative to the speaker's median.

## Alignment and IPA come from Azure now, with an open fallback

**Forced alignment (need 3).** For the app's fixed sentences, Azure's syllable and phoneme timestamps already cover alignment. If you ever need a self-hosted path, the accuracy leader is **Montreal Forced Aligner**: MIT code and CC-BY-4.0 models, about 22 ms mean word-boundary error on TIMIT against about 34 ms for WhisperX ([MFA](https://github.com/MontrealCorpusTools/Montreal-Forced-Aligner), [Rousso et al. 2024](https://arxiv.org/pdf/2406.19363)). It is a conda/Kaldi-style install that belongs in a container, not on Vercel. WhisperX (BSD-2) and NeMo NFA give only word or character timing ([WhisperX](https://github.com/m-bain/whisperX), [NFA](https://docs.nvidia.com/nemo-framework/user-guide/latest/nemotoolkit/tools/nemo_forced_aligner.html)). The popular ctc-forced-aligner uses an MMS model by default, which is **CC-BY-NC** ([HF](https://huggingface.co/MahmoudAshraf/mms-300m-1130-forced-aligner)). Charsiu (MIT) does phone-level alignment but has been **stale since 2022** ([GitHub](https://github.com/lingjzhu/charsiu)).

**Phoneme recognition and mispronunciation detection (need 4).** Three commercially usable IPA recognisers exist. The first is `facebook/wav2vec2-lv-60-espeak-cv-ft` (Apache-2.0, ~1.2 GB), which already has an ONNX port for Transformers.js ([HF](https://huggingface.co/facebook/wav2vec2-lv-60-espeak-cv-ft), [ONNX](https://huggingface.co/onnx-community/wav2vec2-lv-60-espeak-cv-ft-ONNX)). The second is **ZIPA** (code MIT, weights CC-BY-4.0, 64M/300M sizes, INT8 ONNX aimed at browsers). Its "-ns" weights are **non-commercial** ([ZIPA](https://github.com/lingjzhu/zipa)). The third is POWSM (CC-BY-4.0, ESPnet, server-side) ([HF](https://huggingface.co/espnet/powsm)). Allosaurus is GPL-3.0 ([GitHub](https://github.com/xinjli/allosaurus)). The most useful project to study or fork is **OpenPronounce** (MIT, 181 stars, pushed 2026-08), an explicit self-hosted Azure alternative. It uses wav2vec2-espeak with no language model to get the IPA actually spoken, espeak-ng for expected phones, edit-distance alignment, and pYIN pitch curves. It reaches **Spearman ρ 0.65 with human scores on speechocean762** ([OpenPronounce](https://github.com/Halleck45/OpenPronounce)). It downloads about 2 × 1.2 GB of checkpoints, so it needs a Python container. For 3,000 clips a month on Modal that would cost under $1 of compute, inside the $30 monthly free credit ([Beam on Modal pricing](https://www.beam.cloud/blog/modal-pricing-explained)). No public Thai-L1 English mispronunciation corpus exists. PELECAN documents Thai learners' errors, such as /l/ and /r/ deletion in clusters and suffix errors, but has no download ([ISC record](https://search.isc.ac/inventory/49/2406652.htm)). Rule checks for dropped final consonants on the Azure phoneme output are therefore the pragmatic Thai-specific layer. Use speechocean762 (Apache-2.0, includes word-stress and sentence-prosody labels) to sanity-check scores ([HF](https://huggingface.co/datasets/mispeech/speechocean762)).

**Text-to-IPA with stress and syllables (need 6).** The plan's CMUdict→IPA choice is confirmed, but no off-the-shelf package does stress *and* syllable boundaries. Build this pipeline at authoring time: [cmu-pronouncing-dictionary](https://github.com/words/cmu-pronouncing-dictionary) (ISC; static data, last release 2021) → your own maximal-onset syllabifier → a hand-written 39-phone ARPAbet→IPA map → ˈ/ˌ placed at syllable onset → JSON per word (`syllables`, `stressIndex`). Keep an author override for ambisyllabic words like "happy". The obvious syllabifier, [kylebgorman/syllabify](https://github.com/kylebgorman/syllabify), has **no license** and has been stale since 2019, so reimplement the roughly 100-line algorithm rather than copying it. For words missing from CMUdict, [g2p_en](https://github.com/Kyubyong/g2p) (Apache-2.0, stale but functional) keeps ARPAbet stress digits. espeak-ng, Python `phonemizer` and phonemizer.js are **GPL-3.0 in practice** ([espeak-ng](https://github.com/espeak-ng/espeak-ng), [phonemizer.js](https://github.com/xenova/phonemizer.js)), so run them only in a build script and commit the generated JSON. Gruut, OpenPhonemizer and piper-phonemize are **archived** ([Gruut](https://github.com/rhasspy/gruut), [OpenPhonemizer](https://github.com/NeuralVox/OpenPhonemizer), [piper-phonemize](https://github.com/rhasspy/piper-phonemize)). [ipa-dict](https://github.com/open-dict-data/ipa-dict) (MIT, active) is a useful cross-check. One caution: Azure's IPA conventions and your CMUdict-derived IPA must be mapped to one symbol set, or learners will see false "errors".

## Reference audio needs non-HD Azure voices and a Praat fallback

**TTS (need 7).** The plan's Azure Neural TTS choice is confirmed, with a sharp caveat. Non-HD Neural voices support `<prosody contour="(0%,+20Hz) (40%,+10Hz)…">`, which places time-indexed pitch targets as percentages of the text's duration. Microsoft warns that **"pitch contour doesn't work on single words and short phrases"**, and that the service clamps unsupported values ([MS Learn SSML](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-synthesis-markup-voice)). That is exactly the risk for tags like "isn't it?". The newer **HD voices (DragonHD, HD Omni) do not support `<prosody>` or `<emphasis>` at all** and vary from run to run ([MS Learn HD](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/high-definition-voices)). Polly's neural and generative voices ignore `pitch` ([AWS](https://docs.aws.amazon.com/polly/latest/dg/prosody-tag.html)). Google allows pitch only around full sentences, with no contour attribute ([Google SSML](https://docs.cloud.google.com/text-to-speech/docs/ssml)). OpenAI, Gemini and ElevenLabs steer delivery with prompts or tags, which is not deterministic. OpenAI's `gpt-4o-mini-tts` also **shuts down on January 6, 2027** ([OpenAI](https://developers.openai.com/api/docs/guides/text-to-speech), [ElevenLabs v3](https://elevenlabs.io/docs/best-practices/prompting/eleven-v3)).

Two practical rules follow. First, **pre-generate all reference audio at authoring time**, store the SSML alongside the lesson, and serve static files. With the Neural free tier of 0.5 million characters per month, TTS cost stays near zero ([Azure pricing](https://azure.microsoft.com/en-us/pricing/details/cognitive-services/speech-services/)). Second, **check every clip automatically** by extracting F0 at the nucleus and the final syllable. Where the contour won't take, especially for sure-vs-unsure tag pairs, reshape the pitch with **Parselmouth's Manipulation/PSOLA**, which can turn a falling tag into a rising one ([Parselmouth](https://github.com/YannickJadoul/Parselmouth)). Alternatively, use pyworld (MIT) resynthesis ([pyworld](https://github.com/JeremyCCHsu/Python-Wrapper-for-World-Vocoder)). Rubber Band and SoundTouch shift pitch only globally and cannot reverse a contour ([SoundTouchJS](https://github.com/cutterbl/SoundTouchJS)). Among open models, Kokoro (Apache-2.0, has kokoro-js) is practical but has no pitch control ([Kokoro](https://github.com/hexgrad/kokoro)). F5-TTS weights are **CC-BY-NC** ([HF](https://huggingface.co/SWivid/F5-TTS)), XTTS-v2 uses the **Coqui Public Model License** ([HF](https://huggingface.co/coqui/XTTS-v2)), and Piper's active fork is now **GPL-3.0** ([piper1-gpl](https://github.com/OHF-Voice/piper1-gpl)). A recorded human voice is still the safest source for the tag-question contrasts.

## Draw, overlay and gamify with small permissive parts

**Visualisation and drawing quiz (need 8).** No open-source "draw the intonation contour and get scored" exercise exists, so the feature is original. Its pieces are all MIT/BSD/ISC. Use [wavesurfer.js](https://github.com/katspaugh/wavesurfer.js) (BSD-3, 10.5k stars) for the waveform, Record, Regions (word/syllable spans with IPA) and Timeline plugins. Use [uPlot](https://github.com/leeoniya/uPlot) (MIT) for a 60 fps live pitch trace, and [visx](https://github.com/airbnb/visx) or [D3](https://github.com/d3/d3) for the result overlay of target band, learner line and IPA ticks. For input, use plain Pointer Events on SVG with [perfect-freehand](https://github.com/steveruizok/perfect-freehand) (MIT) for stroke rendering, or the drop-in [react-sketch-canvas](https://github.com/vinothpandian/react-sketch-canvas) (MIT, active). [react-konva](https://github.com/konvajs/react-konva) (MIT) suits a "drag dots onto four levels" variant. **Skip tldraw**: its custom license requires a license key in production ([LICENSE.md](https://github.com/tldraw/tldraw/blob/main/LICENSE.md)). react-canvas-draw is **archived** ([GitHub](https://github.com/embiem/react-canvas-draw)). Peaks.js is LGPL-3.0 ([GitHub](https://github.com/bbc/peaks.js)).

For scoring, resample the drawing and the target to N points, map y to a continuous 1–4 scale, and combine three parts: per-syllable level match, **sign agreement of the nucleus-to-tail movement** (the pedagogically decisive part), and a banded DTW or discrete-Fréchet distance. Vendor the tiny MIT DTW from [dynamic-time-warping](https://github.com/GordonLesti/dynamic-time-warping) (stale since 2017) or the Fréchet code from [curve-matcher](https://github.com/chanind/curve-matcher) (stale since 2023), and turn off rotation invariance, because rising versus falling must stay different. $1-family gesture recognisers are rotation- and scale-invariant by design, which makes them the wrong tool.

**Trainers to learn from or fork (need 9).** Nothing maintained matches the product, but four repos are worth reading. **OpenPronounce** (MIT) is the phoneme backend reference. **Inton@Trainer 2** (MIT, C++, pushed 2026-10) aligns learner and reference with constrained DTW over several pitch streams and produces a 0–100% score from a normalised "Unified Melodic Profile". It is the best algorithm reference for contour comparison ([inton-trainer-2](https://github.com/zhitko/inton-trainer-2)). **mema-jp/shadowing** splits pitch scoring into shape, amplitude and speed, which is a good rubric to copy, although its license is unclear ([GitHub](https://github.com/mema-jp/shadowing)). **pitch-pair** (MIT) already wires an FSRS scheduler to a pitch minimal-pair drill ([GitHub](https://github.com/JesseRWeigel/pitch-pair)). IntonationCoach is the exact listen→record→overlay flow (Recorder.js + Praat + D3), but it has **no license and has been stale since 2017**, so use it as a UX reference only ([GitHub](https://github.com/danafallon/IntonationCoach)). The 525-star ai-pronunciation-trainer is **AGPL-3.0** ([GitHub](https://github.com/Thiagohgl/ai-pronunciation-trainer)). Several unlicensed ~50-star "2026" pronunciation repos look star-farmed; ignore them.

**Gamification, spaced repetition and mastery (need 10).** The fullest Duolingo-pattern reference is the Code With Antonio "Lingo" tutorial (hearts, XP, quests, leaderboard, shop). The original repo has **no license** ([GitHub](https://github.com/code-with-antonio/nextjs-duolingo-clone)). The MIT re-upload by sanidhyy ships `mascot.svg` and Duolingo-style sounds in `public/` that must not be reused ([GitHub](https://github.com/sanidhyy/duolingo-clone/tree/main/public)). [bryanjenningz/react-duolingo](https://github.com/bryanjenningz/react-duolingo) (MIT, last push 2024-09) is the cleaner UI reference. Every gamification engine found is stale, for example [ActiDoo gengine](https://github.com/ActiDoo/gamification-engine) (2023). **Build XP, streaks (in Asia/Bangkok time) and leaderboards as Supabase tables and views.** For scheduling, use **[ts-fsrs](https://github.com/open-spaced-repetition/ts-fsrs)** (MIT, active), with each sentence × exercise type as a card and the score mapped to Again/Hard/Good/Easy. For per-skill mastery (for example "rise on yes/no" × listen/draw/speak), use Bayesian Knowledge Tracing modelled on **[OATutor](https://github.com/CAHLR/OATutor)** (MIT, React BKT). Fit its parameters offline with [pyBKT](https://github.com/CAHLR/pyBKT) once the class generates data. Recharts or ECharts can draw the dashboards ([Recharts](https://github.com/recharts/recharts), [ECharts](https://github.com/apache/echarts)). For polish, all of these are permissive and active: [Motion](https://github.com/motiondivision/motion), [rive-react](https://github.com/rive-app/rive-react) (the runtime is MIT; the editor is SaaS), [dotlottie-web](https://github.com/LottieFiles/dotlottie-web), [use-sound](https://github.com/joshwcomeau/use-sound)/[Howler](https://github.com/goldfire/howler.js) and [canvas-confetti](https://github.com/catdad/canvas-confetti).

The research literature supports the visual design. Real-time pitch displays improved learners' prosody and generalised to new sentences ([Hardison 2004](https://www.lltjournal.org/item/312/)). Learner-*created* pitch curves improved Mandarin tones over 9 weeks ([Chun et al. 2015](https://escholarship.org/uc/item/2724q6fv)), which is the closest precedent for the drawing quiz. A 4-week web course with instant pitch feedback improved comprehensibility, and learners found **thought groups and prominence harder than tone choice** ([Jiang & Chun 2023](https://informahealthcare.com/doi/abs/10.1080/09588221.2021.1931342)). Thai undergraduates show L1 transfer in English question intonation ([Mahidol](https://repository.li.mahidol.ac.th/items/f9f3e34d-304c-4f09-8689-20f6c25cb67e/full)). Together these argue for stylised, speaker-normalised targets, a short "how to read the line" explainer, one focused piece of feedback per attempt, and paired listen-and-choose perception drills.

## Conclusion

The research shifts where the effort goes, not what the stack is. The hard, novel part of this app is not recording or phoneme scoring, which Azure and small MIT libraries cover. It is the speaker-normalised contour engine and the drawing scorer, and no API or repository supplies either. That makes phase 0a the phase that decides the project. Spend it validating the rule engine and pitchy's octave behaviour on a handful of real Thai learners' recordings, because a tracker that misreads phrase-final creak will mark correct falls as wrong, and no later polish fixes that.

For a ~50-student class project, the license picture is more forgiving than it looks, with one exception. If you publish the code openly under a GPL-compatible license, most GPL warnings disappear, and the GPL tools are confined to build scripts and servers anyway. AGPL code, the non-commercial weights and unlicensed repos still block any later reuse or commercialisation, so keep them out from day one (this is an inference about licensing, not legal advice). Cost is a non-issue at this scale. Free tiers absorb Azure scoring and pre-rendered TTS, so only Claude calls carry a variable cost, and the budget risk is near zero.
